Map Details

Data sources (all keyless/open): boundary & basemap — OpenStreetMap (Nominatim, OpenFreeMap); elevation & temperature — Open-Meteo; water bodies & protected areas — OpenStreetMap via Overpass (boundary=protected_area/national_park, leisure=nature_reserve); NDVI & elevation-relief — NASA GIBS; vegetation/land-cover — ESA WorldCover via VITO Terrascope. Protected-area boundaries stored as OSM relations (e.g. national parks split across many member ways) are assembled into polygons client-side — a production build would do this server-side and cache it, the same as the boundary/water-body caching already planned. Known gap, not yet fixed: OSM's landuse=residential covers only ~1,900 polygons for this district against ~411,000 individual buildings, and the base map's building layer is itself absent below zoom 13 in the underlying tileset (both verified live) — so settlement extent under-represents reality at district zoom. A WorldCover-Built-up-derived overlay was tried and reverted: at real-city density it painted as a solid tan wash indistinguishable from "barren" and buried the building color underneath it, so it needs a different visual treatment (lower opacity, a distinct hue, or zoom-restricted) before it's worth reintroducing. · Every raster overlay (3D terrain, vegetation, NDVI) is restricted to the region's own bounding box via each source's bounds — tiles outside it are never requested, not just hidden. The map is also leashed to the region via maxBounds. A fully opaque mask then clips the visible render to the exact region shape. Real elevation data drives the 3D terrain toggle: AWS's elevation-tiles-prod DEM tiles send no CORS headers so a browser can't decode them directly, so this prototype's local dev server proxies them same-origin (see serve-prototype.mjs) — the same fix production will apply via a Next.js API route.
